# InspectionList

Журнал осмотра ВЛ. Обходчики заводят листки осмотра по линиям и отмечают на них дефекты по опорам, мастер потом пишет заключение и отмечает устранение. Есть выгрузка в Excel.

Работает в браузере и как Android-приложение на планшетах (Capacitor). На планшете можно работать без сети, данные досылаются на сервер, когда связь появится.

Используется в Гомельских, Жлобинских, Мозырских и Речицких ЭС. Только внутри сети предприятия, наружу сервер не публикуется.

## Как устроено

Бэкенд: Node.js + Express, база Firebird 3+ (рабочие базы — Firebird 5). Фронт: React 18 + TypeScript, собирается Vite. Express отдаёт и API, и собранный фронт из `dist/`, всё на одном порту.

Один сервер приложения и пять баз:

- базы филиалов с листками, дефектами и справочниками: `db/gomel.fdb` (Гомельские ЭС), `db/zhlobin.fdb` (Жлобинские ЭС), `db/mozyr.fdb` (Мозырские ЭС), `db/rechitsa.fdb` (Речицкие ЭС);
- отдельная база пользователей `db/users.fdb`: все учётные записи (логин, хеш пароля, ФИО, роль, филиал) и права ролей. С листками и дефектами она не связана. В git её не хранить (есть в `.gitignore`).

На странице входа пользователь выбирает свой филиал (наблюдатели — «РУП «Гомельэнерго»»); без выбора филиала входит только администратор системы. Логин уникален во всех филиалах. После входа все запросы идут в базу филиала пользователя (`server/lib/fbDb.js`, контекст `AsyncLocalStorage`). Наблюдатель РУП выбирает филиал в шапке — тогда запросы идут в базу выбранного филиала (заголовок `X-Filial-Id`).

Базу пользователей сервер создаёт сам при первом запуске (`server/lib/usersDb.js`): таблицы `FILIALS`, `USERS`, `USER_ALLOWED_LINES`, `USER_ALLOWED_VOLTAGES`, `ROLE_PERMISSIONS`. Пользователи переносятся из таблиц `USERS` баз филиалов (хеши паролей копируются как есть). После этого таблицы `USERS` в базах филиалов не используются, их можно очистить.

Схема примерно такая:

```
браузер / планшет  --HTTP, JSON, Bearer JWT-->  Express (server/index.js)  --node-firebird-->  Firebird
```

Что используется:

- фронт: React 18, TypeScript, Redux Toolkit + RTK Query, SCSS modules, Dexie (IndexedDB), ExcelJS
- Android: Capacitor 8
- сервер: Express 4, jsonwebtoken, bcryptjs, express-rate-limit, node-firebird, dotenv

Зависимости фронта в `package.json` / `yarn.lock`, сервера в `server/package.json` / `server/package-lock.json`.

## Авторизация

Логин через `POST /login` (`{ username, password, filialId }`: номер филиала, `rup` для наблюдателей РУП; без `filialId` — только администратор системы), сервер проверяет пароль по таблице `USERS` базы пользователей и отдаёт JWT-токен на 8 часов (срок меняется в `JWT_EXPIRES`). В токене лежат id пользователя, филиал, роль и списки разрешённых линий/напряжений. Фронт хранит токен в sessionStorage и шлёт в `Authorization: Bearer ...`. Если сервер ответил 401, фронт выкидывает на страницу логина. После 8 часов надо войти заново.

Пароли в базе хранятся в bcrypt. В старой версии хранили в SHA-256, у кого-то такие ещё могут остаться. Когда такой пользователь входит, сервер сам пересохраняет его пароль в bcrypt.

На `/login` стоит лимит 5 попыток за 15 минут.

Офлайн-вход на планшете. Если сервер не ответил за 8 секунд, фронт проверяет пароль локально (`src/features/Auth/model/loginThunk.ts`, по одной учётке на филиал, в сборку попадает только свой филиал по `VITE_FILIAL_ID`). Токена в офлайне нет, всё созданное копится в локальной очереди и уходит на сервер после нормального входа.

Роли:

- `admin` без филиала — администратор системы. Создаёт пользователей всех филиалов и наблюдателей РУП, назначает роли, меняет логины, задаёт временные пароли любому пользователю, настраивает права ролей.
- `admin` с филиалом — администратор филиала: пользователи только своего филиала (пользователей РУП и других филиалов не видит).
- `director` (руководитель), `engineer` (инженер), `master` (мастер), `viewer` (пользователь) — работа с данными своего филиала. Что именно может каждая из этих ролей, задаёт администратор системы (см. ниже). Для engineer предусмотрены ограничения по напряжениям (`USER_ALLOWED_VOLTAGES`), для master по линиям (`USER_ALLOWED_LINES`).
- `observer` — наблюдатель РУП «Гомельэнерго» (1–2 человека): без филиала, на входе выбирает «РУП «Гомельэнерго»», в шапке переключает филиал и смотрит его листки и журнал. Только просмотр: любые изменяющие запросы сервер отклоняет (`blockReadOnlyWrites` в `server/lib/auth.js`).

Права ролей. Администратор системы в «Пользователи → Роли и права» отмечает, что может каждая роль. Права (`server/lib/permissions.js`): создавать/копировать, редактировать, объединять, удалять листки; добавлять, редактировать, удалять дефекты; отмечать устранение; заключение мастера в журнале; выгрузка в Excel; паспорт линии. Хранятся в таблице `ROLE_PERMISSIONS` базы пользователей, при первом запуске заполняются значениями по умолчанию. Сервер проверяет право в каждом изменяющем запросе (`requirePermission`), интерфейс скрывает недоступные кнопки (`usePermissions` в `src/entities/User`). Просмотр доступен всем ролям.

Пользователями управляют в админ-панели `/admin` («Пользователи» в шапке). Логин уникален во всех филиалах. Филиал пользователя после создания не меняется.

Временные пароли. Новый пользователь и пользователь, которому администратор задал пароль, получают признак `USERS.MUST_CHANGE_PASSWORD = 1`: после входа приложение показывает только экран смены пароля, а сервер до смены отвечает 403 на всё, кроме `/changePassword`. Новый пароль: не менее 8 символов, буквы и цифры. Свой пароль можно сменить в любой момент — клик по имени в шапке.

Логинов и паролей пользователей в файлах настроек нет — только в базе пользователей. Если администратора системы в базе нет (новая установка), сервер при запуске создаёт пользователя `admin` со случайным временным паролем и один раз выводит его в консоль; при первом входе пароль нужно сменить.

Порядок middleware в `server/index.js`:

1. фильтр по IP, если задан `BIND_HOST`
2. `express.json`, лимит тела 1 МБ
3. заголовки безопасности (`X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, CSP) и CORS
4. статика из `dist/`
5. `authMiddleware`: разбирает JWT, заполняет `req.userId`, `req.filialId`, `req.role`
6. `tenancyMiddleware`: считает, какие линии доступны филиалу
7. проверка авторизации (`requireAuth`)
8. выбор базы филиала (свой филиал или `X-Filial-Id` для пользователей без филиала)
9. `blockReadOnlyWrites` (наблюдатель РУП) и `blockUntilPasswordChanged` (временный пароль)
10. роуты (изменяющие — с проверкой прав роли `requirePermission`)
11. SPA fallback: неизвестный GET отдаёт `index.html`
12. обработчик ошибок

Для локальной разработки есть режим `VITE_ENABLE_MOCK_AUTH=true`: сервер берёт пользователя из заголовков `X-User-Id` / `X-Filial-Id` / `X-Role` без токена. С `NODE_ENV=production` сервер с этим флагом не запустится.

## Разделение по филиалам

У каждого филиала своя база, пользователь филиала работает только с ней. Кроме того, в `server/lib/tenancy.js` при старте строится карта «филиал -> id линий» по `LINES.FILIAL_ID` и `FILIAL_VOLTAGE_FILTER`, и роуты фильтруют данные через `canAccessLine` / `lineWhereClause`. Карта строится один раз при старте, после правки справочника линий сервер надо перезапустить.

## API

Всё JSON.

Пользователи, `server/routes/auth.js`:

| метод | путь | что делает |
|---|---|---|
| POST | `/login` | вход, выдаёт токен |
| GET | `/users` | список пользователей (администратор системы — все, администратор филиала — своего) |
| GET | `/users/me` | текущий пользователь |
| POST | `/users` | создать пользователя |
| PATCH | `/users/:id` | изменить пользователя |
| DELETE | `/users/:id` | удалить пользователя |
| POST | `/users/:id/resetPassword` | задать временный пароль пользователю |
| POST | `/changePassword` | сменить свой пароль |

Для `PATCH` / `DELETE` / `resetPassword` указывается `?filialId=` — филиал пользователя (пусто — пользователь без филиала).

Права ролей, `server/routes/permissions.js`:

| метод | путь | что делает |
|---|---|---|
| GET | `/permissions/me` | права текущего пользователя |
| GET | `/rolePermissions` | все права и их распределение по ролям (администратор системы) |
| PUT | `/rolePermissions/:role` | сохранить права роли (администратор системы) |

Листки, `server/routes/sheets.js`:

| метод | путь | что делает |
|---|---|---|
| GET | `/inspectionSheets` | список листков с фильтрами и пагинацией |
| GET | `/inspectionSheets/:id` | один листок |
| POST | `/inspectionSheets` | создать листок |
| POST | `/inspectionSheets/:id/clone` | копия листка на другую дату |
| PATCH | `/inspectionSheets/:id` | изменить листок |
| DELETE | `/inspectionSheets/:id` | удалить листок |
| POST | `/inspectionSheets/merge` | объединить несколько листков в один |

Дефекты, `server/routes/defects.js`:

| метод | путь | что делает |
|---|---|---|
| GET | `/defectRecords` | список дефектов |
| GET | `/defectCounts`, `/defectTrends`, `/poleDefectStatus` | счётчики и статистика |
| POST | `/defectRecords` | добавить дефект |
| PATCH | `/defectRecords/:id` | изменить дефект (заключение, устранение и т. д.) |
| DELETE | `/defectRecords/:id` | удалить дефект |
| DELETE | `/defectRecordsBySheet/:sheetId` | удалить все дефекты листка |

Справочники, `server/routes/reference.js`:

| метод | путь | что делает |
|---|---|---|
| GET | `/filials`, `/voltages`, `/lines`, `/filialVoltageFilter` | справочники филиала (`/filials` для пользователя без филиала — все филиалы) |
| GET | `/elements`, `/defectTypes`, `/phases`, `/phaseElementIds` | общие справочники |
| PATCH | `/lines/:id` | изменить паспорт линии |

Синхронизация, `server/routes/sync.js`:

| метод | путь | что делает |
|---|---|---|
| POST | `/sync/batch` | принять пачку изменений с планшета |
| GET | `/sync/pull` | отдать все данные филиала |

SQL везде параметризованный (`?`). Имена колонок в динамических UPDATE берутся только из захардкоженных списков.

## Где лежат данные

На сервере Firebird, базы лежат в `db/`.

Базы филиалов:

- справочники: `FILIALS`, `VOLTAGES`, `LINES`, `ELEMENTS`, `DEFECT_TYPES`, `PHASES`, `PHASE_ELEMENT_IDS`, `FILIAL_VOLTAGE_FILTER`
- `INSPECTION_SHEETS`: листки (одна линия на одну дату, уникальный индекс)
- `DEFECT_RECORDS`: дефекты, заключения мастера, устранение

База пользователей `users.fdb`:

- `USERS`: логин, хеш пароля (bcrypt), ФИО, роль, филиал, `MUST_CHANGE_PASSWORD`; плюс `USER_ALLOWED_LINES` и `USER_ALLOWED_VOLTAGES`
- `ROLE_PERMISSIONS`: права ролей
- `FILIALS`: список филиалов

Справочники для интерфейса (филиалы, напряжения, линии, элементы, виды дефектов) встроены в сборку из `server/seed/*.json` — чтобы планшет работал без сети. В `server/seed/` лежат данные всех четырёх филиалов, в подпапках `1`…`4` — по филиалам.

Из персональных данных только ФИО сотрудников: кто создал листок, кто нашёл и устранил дефект, мастер, отображаемое имя пользователя.

К базам сервер подключается под служебной учётной записью Firebird `FB_USER` / `FB_PASSWORD` из `server/.env` (это не пользователь приложения). Доступ к `server/.env` — только у администратора и учётной записи сервера.

На клиенте (браузер / WebView):

- sessionStorage: `defect_tracker_token` (JWT), `defect_tracker_user` (профиль), `defect_tracker_view_filial` (филиал, выбранный наблюдателем РУП)
- localStorage: `api_server_url` (адрес сервера, задаётся на планшете вручную), `pending_sheets_v1` и `pending_defects_v1` (офлайн-очередь), `defect_tracker_inspector` (последнее введённое ФИО), `theme`
- IndexedDB `InspectionListDB`: кэш листков, дефектов, справочников

## Настройки

`server/.env`:

```
PORT=8443            # у нас на серверах 80
BIND_HOST=           # пусто = 0.0.0.0
FB_HOST=127.0.0.1
FB_PORT=3050
FB_DATABASE_1=       # база Гомельских ЭС (номер = ID филиала)
FB_DATABASE_2=       # база Жлобинских ЭС
FB_DATABASE_3=       # база Мозырских ЭС
FB_DATABASE_4=       # база Речицких ЭС
FB_DATABASE_USERS=   # база пользователей (создаётся сервером при первом запуске)
FB_USER=
FB_PASSWORD=         # обязательно, без него сервер не стартует
JWT_SECRET=          # в production обязательно, от 32 символов
JWT_EXPIRES=8h
BCRYPT_ROUNDS=12
NODE_ENV=production  # включает проверки конфига
```

Секрет можно сгенерить так:

```
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

Фронт (`.env`, `.env.production.local`), это всё уезжает в бандл, секретов туда не класть:

- `VITE_API_URL`: адрес API; в dev на него проксирует Vite. На ноутбуке разработки — `http://localhost` (сервер запускается тут же), рабочий сервер — `http://10.180.160.167`
- `VITE_FILIAL_ID`: филиал сборки для входа на планшете без сети (1 Гомель, 2 Жлобин, 3 Мозырь, 4 Речица). На вход через сервер не влияет

## Установка

Нужно: Node.js 18+, Yarn, Firebird 3.0+. Для APK ещё Android Studio и JDK 17.

База:

1. скопировать базы филиалов из `db/` на сервер Firebird
2. прописать пути к ним (`FB_DATABASE_1` … `FB_DATABASE_4`), путь к базе пользователей (`FB_DATABASE_USERS`) и учётные данные Firebird в `server/.env`
3. запустить сервер: при первом запуске он создаст базу пользователей и перенесёт в неё пользователей из баз филиалов

Сервер:

```bash
cd server
npm ci
# заполнить server/.env
cd ..
yarn install
yarn build
node server/index.js
```

На серверах крутится через pm2: `pm2 start server/index.js --name inspectionlist`.

APK:

```bash
# в .env выставить VITE_FILIAL_ID и VITE_API_URL
yarn deploy      # build + cap sync
```

Дальше собрать в Android Studio из папки `android/`. Адрес сервера на планшете меняется без пересборки, шестерёнка рядом с кнопкой «Синхронизировать».

## Разработка

```bash
yarn install
cd server && npm install && cd ..
yarn start
```

`yarn start` поднимает Vite на :3000 и сервер, API проксируется на `VITE_API_URL` (на ноутбуке разработки — локальный сервер с базами из `db/`).

Ещё команды:

- `yarn build`: tsc + сборка в `dist/`
- `yarn start:prod`: vite preview + сервер
- `yarn deploy`: сборка + cap sync
- `yarn lint:ts`, `yarn lint:scss`
- `yarn check:all`: типы и линтеры

## Структура

```
src/          фронт, раскладка по Feature-Sliced Design
  app/        роутер (RequireAuth), store, тема
  pages/      Login, SheetsList, SheetDetail, Journal, Users (админ-панель), ForcePasswordChange, NotFound
  widgets/    Navbar, SheetsList, DefectTable, GlobalDefectSearch
  features/   Auth, ChangePassword, FilialSwitcher, AddDefect, CopyDefect, FixDefect, CreateSheet, ExportToExcel, SyncToServer ...
  entities/   InspectionSheet, DefectRecord, InspectionLine, User (роли, права, пользователи)
  shared/     rtkApi, localDb, офлайн-очередь, ui-kit, стили
server/
  index.js    вход, middleware
  lib/        auth.js, tenancy.js, fbDb.js (базы), usersDb.js (база пользователей), permissions.js (права ролей), schema.js, config.js
  routes/     auth, permissions, sheets, defects, reference, sync
  seed/       справочники (все филиалы; по филиалам — в 1…4)
db/           базы филиалов .fdb и users.fdb
android/      проект Capacitor
```

Страницы: `/login`, `/sheets` (список листков), `/sheet/:id` (листок с дефектами), `/journal` (журнал, заключения мастера), `/admin` (пользователи и права ролей, для администраторов), остальное 404. Страницы кроме `/login` закрыты `RequireAuth` на фронте.
